# 缺陷单

10类跟踪问题，全部未修复。20条失败用例不等于20个缺陷。

## TAKE-001 订单状态未校验

建议优先级：P1；状态：未修复。

关联用例：ORD-006/007

复现步骤：先按0→1→2→3更新QA_ORDER_1，再发送状态0和255。

实际表现：完成订单可回退为0；非法状态255可保存。

根因位置：commmsgmanager.cpp / processOrderMenuList

原因分析：未检查状态枚举和流转条件，直接替换已有订单。

修复建议：按角色和原状态校验转换；条件更新防止过期状态覆盖。

## TAKE-002 负金额与负菜品价格可保存

建议优先级：P1；状态：未修复。

关联用例：ORD-008、MENU-005

复现步骤：发送负price字段，读取SQLite金额。

实际表现：订单金额-1、菜品价格-3均落库。

根因位置：databaseinterface.cpp / insertMenuOrderInfo、insertCustomMenu

原因分析：服务端直接使用客户端传入价格，缺少范围校验。

修复建议：校验金额范围，订单由服务端根据商品和数量计算。

## TAKE-003 批内重复业务标识产生重复记录

建议优先级：P1；状态：未修复。

关联用例：ORD-009、MENU-008/009

复现步骤：同一报文携带两条QA_DUP或QA_MENU_A；再提交混合A/B商户菜单。

实际表现：重复UUID订单和菜单均保存多条；混合商户批次造成B商户重复菜品。

根因位置：commmsgmanager.cpp / processOrderMenuList、processInsertCustomMenuList

原因分析：订单去重列表只在循环前读取；菜单处理仅按第一条的商户删除，表缺唯一约束。

修复建议：使用业务唯一约束和批内去重；按商户分组处理并原子提交。

## TAKE-004 单引号导致保存失败或原数据丢失

建议优先级：P1；状态：未修复。

关联用例：REG-007、MENU-006、ORD-010/011

复现步骤：先保存普通名称，再将名称更新为Chef's rice；比对前后记录。

实际表现：O'Neil账号无法保存；Chef's rice菜品与订单更新失败，旧菜单或旧订单消失。

根因位置：databaseinterface.cpp / insertUserInfo、insertCustomMenu、insertMenuOrderInfo；commmsgmanager.cpp

原因分析：SQL通过字符串拼接，单引号破坏语句；先删除后插入缺少整体事务。

修复建议：使用参数绑定；原子更新或事务回滚保留旧记录。未将此测试宣称为SQL注入验证。

## TAKE-005 未认证UDP来源可写订单

建议优先级：P1；状态：未修复。

关联用例：AUTH-001

复现步骤：新建未配置源端口，直接发送0xaaff订单报文。

实际表现：未配置的新UDP来源，不登录即可创建QA_UNAUTH。

根因位置：commmsgmanager.cpp / slotNetworkDatagramNotify、processOrderMenuList

原因分析：按消息头直接执行写入，未验证会话身份或权限。

修复建议：加入服务端认证及角色授权；不能仅靠客户端按钮隐藏。

## TAKE-006 注册字段与角色范围未校验

建议优先级：P2；状态：未修复。

关联用例：REG-006/008

复现步骤：发送空姓名账号与角色255账号，核对userinof表。

实际表现：空用户名可保存，非法角色255被保存为-1。

根因位置：parsedata.cpp / execute(UserInfo)；databaseinterface.cpp / insertUserInfo

原因分析：固定长度检查后直接转换及入库，缺少业务字段校验。

修复建议：明确字段必填、账号规则及角色枚举；管理员注册增加授权。

## TAKE-007 大金额小数精度丢失

建议优先级：P1；状态：未修复。

关联用例：ORD-012

复现步骤：发送QA_PRECISION订单price=123456.78并查询数据库。

实际表现：请求123456.78，保存为123457；0.01与9999.99场景通过。

根因位置：databaseinterface.cpp / insertMenuOrderInfo

原因分析：QString::arg(double)默认有效数字格式在拼接SQL时丢失精度。

修复建议：采用绑定参数；金额以整数分或明确精度的定点类型存储；产品金额上限待评审。

## TAKE-008 手机号返回客户端时被截断

建议优先级：P1；状态：未修复。

关联用例：DATA-001

复现步骤：注册11位合成手机号，再发0xaabb列表请求，解析响应手机号并与库比较。

实际表现：SQLite为13900000001，UDP返回1015098113。

根因位置：databaseinterface.cpp / getUserInfoList

原因分析：读取phoneNum时调用toUInt，仅保留32位，而接口字段使用64位。

修复建议：手机号优先使用字符串；或使用toULongLong并对边界回归。

## TAKE-009 未登录可获取账号列表中的明文密码

建议优先级：P1；状态：未修复。

关联用例：AUTH-002

复现步骤：不建立登录会话，发送0xaabb，检查账号响应密码字段。

实际表现：未登录请求返回测试用户列表及可用的合成密码。

根因位置：commmsgmanager.cpp / processUserinfoList；makedata.cpp / makeUserinfoListData

原因分析：列表响应包含密码，且请求未认证；客户端通过列表匹配密码。

修复建议：认证迁至服务端；密码安全散列存储，不经用户列表返回。仅测试合成账号，未访问原用户数据。

## TAKE-010 订单必要字段缺失仍保存

建议优先级：P2；状态：未修复。

关联用例：ORD-014/015/016

复现步骤：依次发送缺少上述字段的独立订单报文，核对是否落库。

实际表现：空订单UUID、空客户UUID、空菜品名称的订单均被接受。

根因位置：commmsgmanager.cpp / processOrderMenuList；databaseinterface.cpp / insertMenuOrderInfo

原因分析：仅验证包长，未验证字段业务含义；NOT NULL不拒绝空字符串。

修复建议：校验业务标识与必要字段；确认客户关联和订单内容。
